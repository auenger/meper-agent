明确结论
是。当前实现属于“级联式应用层全双工语音架构”。

浏览器到后端使用同一条 WebSocket 同时承载麦克风 PCM 上行、TTS PCM 下行和 JSON 控制事件；浏览器在播放 Agent 回复时仍持续采集语音，本地 VAD 检测到用户开口后会立即清空播放并取消当前 Agent/TTS 任务。

传输层全双工 WebSocket
交互层可边听边说 / Barge-in
模型层ASR → Agent → TTS 级联
不属于端到端 Audio-to-Audio

系统总览

三段实时连接由 VoiceSession 统一编排；主聊天与语音共用 Agent、session_id 和消息 timeline。

双工边界拆解

“双工”在不同连接上的强度不同，实际体验由这些能力组合而成。

链路技术形态判断说明
浏览器 ⇄ FastAPI单条 WebSocket：JSON + Binary全双工麦克风 PCM 上行与 TTS PCM 下行可同时发生；控制消息可随时穿插。
FastAPI ⇄ Seed ASRbigmodel_async WebSocket双向流式后端持续发送 200ms 音频块，同时接收 partial / final 识别事件。
FastAPI ⇄ Seed TTSbidirection WebSocket协议双向使用双向会话事件；当前业务按句发送文本、流式接收 PCM，并非逐字符持续输入。
Agent ⇄ TTS Pump异步 sentence queue并行流水线Agent 继续生成后文时，前面完整句已经进入 TTS，降低首包等待。

打断路径： listening 期间始终保持音频采集；当 speaking / thinking 状态检测到 Speech.START，发送 playback.clear，取消 LLM task、TTS task 和当前 TTS Session，随后回到 listening。

低延迟与稳定性设计

这里的性能不是单点优化，而是跨浏览器、协议和任务编排的组合。

20 ms浏览器 PCM16 上行帧；采集率统一重采样到 16kHz。
200 msASR 客户端聚合块；平衡网络开销与实时识别延迟。
1.0 spartial idle commit 兜底；噪声导致 VAD 不结束时仍能提交文本。

音频与播放

  • Web Audio 将原生采样率重采样到 PCM16 mono 16kHz。
  • 下行 PCM16 24kHz 使用时间游标无缝排程，避免片段间爆音和空隙。
  • 打断会停止所有已排程 AudioBufferSourceNode，并重置未来播放游标。
  • 浏览器启用回声消除、降噪和自动增益，降低播放回灌。

任务与连接

  • Agent 流与 TTS pump 分为独立异步任务，句子一完成即可合成。
  • Turn lock 保证同一连接内轮次串行，barge-in 通过任务句柄主动取消。
  • 被取消的火山 TTS WebSocket 直接废弃，下一轮重连，避免残留 SessionCanceled 污染。
  • ASR 每次本地提交后重建上游流，避免累积转写污染下一句话。

协议与配置

语音模型固定使用 Agent Plan 指定 Resource-Id，不参与 Auto 调度。

浏览器 ⇄ Backend

  • WS /api/v1/voice/realtime?token=JWT
  • 上行二进制：PCM16 LE · mono · 16kHz。
  • 下行二进制：PCM16 LE · mono · 24kHz。
  • 控制：voice.start、voice.stop、interrupt、audio.info。
  • 事件：voice.state、transcript.*、agent_text_delta、playback.clear。

Volcengine Agent Plan

  • ASR Resource-Id：volc.seedasr.sauc.duration
  • ASR：/api/v3/plan/sauc/bigmodel_async
  • TTS Resource-Id：seed-tts-2.0
  • TTS：/api/v3/plan/tts/bidirection
  • 鉴权：专属 X-Api-Key；后端加密存储，不下发浏览器。

当前架构刻意没有做什么

这些边界决定了系统应被称为“级联式全双工”，而不是“原生端到端双工”。

不是 WebRTC 媒体栈

当前传输基于 WebSocket + 原始 PCM，没有 RTP、DTLS、抖动缓冲、带宽自适应或 Opus 编码。局域网和常规 Web 对话足够直接，但弱网能力不等同于实时通信平台。

不是 Audio-to-Audio 模型

语音先转文字，再进入 Agent，最后将文本转回音频。它保留了工具调用、Markdown、会话记录与传统 Agent 能力，但不直接建模语气和声学上下文。

TTS 不是逐字符输入

虽然接入的是 bidirection 协议，当前通过 sentence queue 按完整句发起 TaskRequest。这样更稳定、便于 Markdown 清洗，但极限首音延迟仍可继续优化。
